# Owner login and a usable chat application

> This is the original design/acceptance plan. For current implementation and
> verification status, see [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md).
> Historical preview limitations below describe the planning baseline.

14 October 2026. Product requirement and implementation sequence; **the owner-login service below is not implemented in the static preview**. This supersedes earlier plans that treated account-free, memory-only browser pairing as the finished product.

The product is a private, self-hosted application for the person who installs it. No vendor account or vendor credential/content service is required. Owner-controlled authentication and configuration storage are allowed. Hermes remains an independent server, on any supported host. The first opening of a newly installed instance must create its administrator login.

## Owner flow

1. One installation agent deploys the app and plugin, prepares their persistent configuration and trust, verifies the actual connection route, and returns the app URL. The web host and Hermes host are independent choices. No owner needs to select a bridge port, enter CORS settings, find a Hermes API key, or relay diagnostics to a second agent.
2. First opening shows **Create your administrator login**, with credentials chosen by the owner. This creates the administrator of this instance, not an account with us. Setup needs proof of installation ownership; an unclaimed public URL must not be claimable by its first visitor. The installer provisions a one-use setup credential delivered privately to the owner, separate from the URL. There are no default passwords or open registration.
3. Guided setup detects the installation's primary existing agent, shows that identity, and asks the owner to keep or change its public @ handle, avatar shape and color in one confirmation step. Existing appearance or a default can be kept with no extra mandatory step. It enables that same profile as the initial orchestrator and opens its native Bot Chat with a verified one-time welcome. Do not make a profile picker the normal first-run task or guess from roster order; ambiguous detection needs an actionable installation check. The handle remains editable in Settings without renaming or cloning the native profile. See the [onboarding and connections plan](ONBOARDING_AND_CONNECTIONS_PLAN.md) and [team/orchestrator contract](TEAMS_AND_ORCHESTRATOR_PLAN.md). The owner can then choose additional existing Hermes agents in the app. Search and scroll work with a real-sized roster. The same profiles, SOUL, memory, skills, model settings and native Bot Chats are used. No placeholder is created and no persona is copied.
4. Subsequent visits show the workspace while the owner session remains valid, or an ordinary sign-in form when it has expired. Browser refresh, app/Hermes restart and temporary network loss do not require a Hermes agent or a new approval code. Signing in on a new device must likewise use the instance login, not an agent-mediated device registration.
5. Sign out, revoke other sessions, or change the password through the owner instance. Losing an app session may require signing in again; it does not require configuring Hermes again. Stop remains a separate explicit native action; closing the page does not stop running agents.

## Authentication boundary and deployment

A client-side password gate would not protect configuration or APIs. Add a small owner-hosted authentication service alongside the web assets. It may run far away from Hermes and must not require a server-to-server route to the home network. No runtime or storage is hosted in a vendor account on the owner's behalf.

| Deployment                         | App runtime and owner state                                                                                               | Hermes                                      |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| VPS, home server or container host | Node runtime, local SQLite file, persistent secret/config directory or volume; no separately administered database server | Independent supported host                  |
| Owner's Cloudflare account         | Worker with static assets and a small D1 database for the same owner state; secrets in that owner's account               | Independent supported host                  |
| Plain static hosting only          | Still usable as the explicit technical preview; insufficient by itself for the required local administrator login         | Independent bridge, current preview pairing |

Both launch deployments must have the same user flow and authentication contract. Cloudflare is an adapter, not a mandatory service. This changes the earlier static-only product assumption; it does not change the independent-host requirement. Cloudflare supports [Worker code with static assets](https://developers.cloudflare.com/workers/static-assets/) and [running it before asset delivery](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/).

Use a maintained authentication library, rather than building password/session cryptography into the UI. Better Auth is a candidate with documented [SQLite drivers](https://better-auth.com/docs/adapters/sqlite), [username support](https://better-auth.com/docs/plugins/username), and [session/CSRF/password protections](https://better-auth.com/docs/reference/security). Selection is conditional on a Node/Cloudflare proof of concept, dependency audit and atomic bootstrap tests; these docs alone do not establish runtime compatibility. Store password hashes, not passwords. Session cookies must be Secure and HttpOnly, with explicit same-site, expiry, renewal, CSRF and logout semantics. Rate limits and failed-attempt state cannot disappear on a routine restart. Disable public registration and third-party accounts by default. An owner-local recovery command replaces dependence on a vendor email/password-reset service.

## Connect once, renew automatically

Prefer a narrowly scoped issuer relationship instead of placing the Hermes administrator key in the browser or app database:

- The installation agent provisions a per-instance signing key in the owner's app secrets and registers only its public verification key, issuer, audience and exact allowed web origin in persistent plugin configuration. Trust enrollment is operator-controlled and never based on a browser-supplied issuer, key URL or JWT header.
- After an authenticated owner session and CSRF validation, the app issues a short-lived, origin-bound native-client ticket. The browser uses it directly with the Hermes plugin. Tickets have fixed algorithm, issuer, audience, subject/session, issued-at, expiry and scope validation. The ticket cannot call operator pairing/revocation APIs or arbitrary native RPC.
- The app server does not need to reach the private Hermes address. It issues tickets locally; the browser must still have network access to Hermes through the owner's chosen trusted HTTPS route. It can renew tickets through its existing login session without a code exchange.
- Browser tickets stay in memory. The instance holds its administrator/session/configuration state, and the plugin persists its verification trust, so process restarts do not destroy the relationship. Backups and updates preserve these stores. Never auto-generate replacement secrets on top of an existing installation when a required key is missing.
- Short-lived tickets impose a defined maximum revocation delay. The protocol must explicitly test logout, password change, session revocation and issuer rotation, including already open streams. Do not promise immediate global revocation without implementing it. Set the final ticket lifetime and revocation strategy in the authentication spike before freezing the wire contract.

This is the proposed implementation design, not an existing plugin capability. Keep legacy preview pairing as a clearly labeled migration path, not the primary owner onboarding. Do not ship a browser credential saved indefinitely as a substitute for the requested instance login.

No chat, message draft, SOUL, memory, model credential or transcript is stored by the app service. Its configuration/authentication data belongs to the owner on their deployment. Conversation traffic remains browser-to-Hermes; all model execution and canonical history remain native. Auth/configuration endpoints, browser tickets and session cookies must be excluded from request/response logs and caches. No telemetry or remotely loaded transcript images.

## Work sequence and acceptance

1. **Repair the current test UI.** Verify 28-agent scrolling and action reachability at laptop and phone sizes; add search. Repair composer focus/growth, draft isolation, safe rich replies and history scrolling. Leave the real Hermes connection working and avoid requiring a plugin reinstall for these web-only changes.
2. **Implement the owner-authentication vertical slice.** Node/SQLite and Cloudflare/storage adapters behind one Fetch-style API. Atomic single-admin bootstrap, ordinary login, persistent sessions, CSRF/rate limits, logout/revocation, and owner-local recovery. Never ship a decorative login that only hides the React UI. Test competing bootstrap requests, unapproved requests, guessed setup codes, restart persistence, cookie scope and account recovery before exposing a public install.
3. **Implement issuer trust and automatic connection recovery.** Version the plugin/protocol changes, verify both supported native builds, migrate an existing installation preserving its profiles and routes, and test independent hosts with the app server unable to reach Hermes. Refresh and reopen after an actual bridge restart must work through the owner login alone. Rebind the native selected chat, restore canonical history/in-flight work/approvals, then allow sending. Never replay uncertain sends or approvals; reconcile history first. Temporary network failure must show reconnecting while actions are blocked, then recover with bounded backoff.
4. **Rebuild the chat experience as a product.** Continue the restrained dark visual direction, but make the conversation primary. Review the complete interaction flow against [Grok Bot's messaging behavior](https://docs.x.ai/grok-bot/chat-and-collaboration), not just its column layout: opening/switching agents, sending, following work, finding earlier messages, handling approvals, steering/stopping work, shared rooms and returning later. Activity belongs with the relevant turn; details/routines are available without permanently crowding the chat. Add only capabilities verified in Hermes; do not draw nonfunctional attachment, voice, reaction or reply controls.
5. **One-agent clean-install acceptance.** Start with ordinary existing profiles and zero managed bots; install to independent app/Hermes hosts, create the first admin, detect the primary existing agent, confirm its handle, run one owner-authorized round trip, close/reopen, interrupt/recover the network, restart the bridge and app safely, and update/roll back without reconfiguration or identity loss. Both deployment adapters need their own evidence. Component success is not a launch pass.

Current preview still lacks the owner-authentication service, durable connection trust, automatic reconnect and proven service supervision. Preserve these as unverified launch gates until the complete installed workflow passes.
