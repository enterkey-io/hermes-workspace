# Animated avatar system plan

15 October 2026. **Architecture and product proposal; not a shipped feature.** Baseline web preview: `0.2.4-preview.2`. This adds appearance choices to the planned onboarding and Settings; it does not imply that authentication, onboarding, connection management, native clients or the proposed persistence API have shipped. An isolated motion demo is a design/engineering experiment, not backend integration or cross-platform certification.

## Recommendation

Build an original family of colored geometric faces with expressive eyes, using a small renderer-independent geometry and motion specification. Start the web implementation with SVG and one shared imperative scheduler. React owns mounting, appearance changes and semantic state changes; it does not render every animation frame. Keep body paths fixed during ordinary motion and animate bounded transforms, eye openness and opacity. Use the same pure pose sampler and versioned fixtures for future native renderers.

Do not choose an entire application framework to solve avatars. Native Apple drawing and a Windows renderer are viable future adapters; a shared webview is also viable if the app architecture independently chooses one. That decision is open. SVG is the first web renderer, not the cross-platform contract. Measure realistic roster loads before introducing Canvas2D, WebGL or a commercial authoring workflow.

All geometry, palettes, motion data and runtime dependencies ship with the owner's installation. Rendering requires no image model, vendor service, external asset URL or telemetry. The app and Hermes may run on separate owner-controlled hosts. Appearance persistence uses the authenticated, verified bot identity binding; it does not require the app server to reach the private Hermes network.

## Evidence and inspiration boundaries

The official [Grok Bot design article](https://x.ai/news/designing-grok-bot) describes consistent simple shapes, expressive eyes, identity recognition and idle/working/waiting/blocked/thinking/done motion. Its embedded reference assets were located during research; this architecture review did not visually verify their exact animated timings or trajectories. The user's observations of gaze, blinking, squinting and opening are design requirements, not independently measured competitor behavior. Do not present inferred animation technology as fact.

The official [motion playground account](https://x.ai/bot/guides/designing-grok-bot-with-grok-bot) describes a local playground around its production animation specification with adjustable timing, springs, position, scale and easing. This supports the value of a tunable specification; it does not disclose a reusable implementation or establish that Grok uses SVG, Rive or any particular renderer. Build original geometry, proportions and choreography. Do not copy their downloaded assets or source.

## Original visual direction

Keep a recognizable two-eye construction across a small family. A geometric body, two eyes and at most one quiet accent should read at 24–40 CSS pixels; larger previews may reveal extra detail. Color must never be the only way to identify a bot or understand status.

Proposed families, subject to preview review:

- **Pebble:** asymmetric rounded stone; soft corners, slight side lean and gentle eye drift.
- **Kite:** rounded diamond with a short off-center lower point; tilt for acknowledgement, stable silhouette during work.
- **Lantern:** squat six-sided form with a broad face; compressed eyes during preparation and alternating small side marks while a tool runs.
- **Orbit:** circular body with a detached short arc; the arc moves only during active work, avoiding constant whole-body rotation.
- **Sprout:** two-lobed capsule with a small integrated crest; a modest upward settle on completion.
- **Fold:** rounded trapezoid with a clipped corner; offset eyes and a restrained edge highlight.

These are original proposals, not descriptions of Grok's exact shapes. Start with four to six well-differentiated silhouettes rather than dozens of near-duplicates. Offer a curated color palette, including white as requested by the owner, plus a validated solid custom color later. The first playground direction is approved; preserve its restrained motion and geometric character family while refining details. Derive eye color from contrast, and test both themes. Do not recolor the bot by status; use a separate status mark/text.

Eye channels: horizontal/vertical gaze, openness, squint amount and optional catchlight offset. Clip pupils inside eye bounds. Blink closes both eyes for a short bounded envelope; a squint can persist briefly without hiding task status. Suggested tuning ranges: blink closure/reopen 100–180 ms total, gaze holds 1.5–4 seconds, body scale within 0.97–1.03, rotations within ±4 degrees. These are starting design values, not observed competitor values. Event reactions can be 180–350 ms; completion accents end within 900 ms.

Use motion sparingly: idle is mostly still with occasional blink/look; preparing/thinking uses a deliberate held look and subtle eyelid change; tool work uses a small repeatable accent; waiting settles into a stable pose; completion performs one short release. Avoid constant bouncing throughout a roster. Pointer-following gaze is optional and limited to the directly hovered large preview; never track global pointer movement for every avatar.

## Renderer decision

| Renderer                        | Strengths                                                                                                                          | Costs and limitations                                                                                                                                                                                                 | Decision                                                                                                                                   |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| SVG + imperative attributes/CSS | Crisp at any size; small plain geometry; easy inline fallbacks, themes and inspection; suits the existing native SVG architecture. | Many animated DOM nodes can raise style/paint cost. SVG transforms are not a guarantee of compositor-only rendering; avoid assuming GPU acceleration. CSS-only timelines complicate deterministic state interruption. | First web renderer. CSS handles layout/static styling; a single sampler/scheduler owns motion.                                             |
| Canvas2D                        | Can batch a dense roster and cache geometry/static layers; avoids per-shape DOM nodes.                                             | Redraw/DPR costs; hit testing and accessibility remain DOM responsibilities; many individual canvases can waste memory. OffscreenCanvas/worker support must be checked in target engines.                             | Benchmark a shared-layer or carefully scoped canvas only if SVG fails target loads. Do not replace accessible controls.                    |
| WebGL                           | Instancing can suit very large counts or richer effects.                                                                           | GPU/context loss, texture/buffer management, platform differences and recovery complexity; a context per avatar is unacceptable.                                                                                      | Defer. A small roster of simple faces does not justify it without measured evidence.                                                       |
| Rive                            | Interactive animation/state-machine authoring and supported runtime families; useful if artists need richer authored animation.    | Additional runtime/asset/tooling weight and feature-version coupling; Windows/native integration still needs a specific supported path and proof. No automatic energy advantage.                                      | Reconsider for a materially richer art direction. Bundle pinned runtime/assets locally; review licenses and authoring workflow separately. |
| Lottie                          | Good for fixed exported sequences and small celebratory effects; established renderers.                                            | Feature parity differs between renderers/platforms. Continuously parametric gaze, interruption and semantic state coordination need an extra controller; large per-avatar players add overhead.                       | Not the core face system. Optional local finite effect only if it beats a few primitives.                                                  |

[MDN Canvas optimization](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas) recommends reducing repeated work and considering cached/layered drawing. [MDN WebGL guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) documents resource and context concerns. Neither establishes a universal winner for this workload. [Rive runtime overview](https://github.com/rive-app/help-center/blob/master/runtimes/overview.md) lists web, Apple/iOS, Android, Flutter and C++ integration families; it is not a guarantee of native Windows drop-in parity. [Lottie renderer feature table](https://github.com/airbnb/lottie-web/wiki/Features) is a reason to certify the exact exported feature subset.

## Shared contract and deterministic motion

Proposed package boundaries:

1. `avatar-spec`: bundled, versioned manifest of silhouettes, palette IDs, normalized paths, eye anchors, safe gaze bounds and motion channels. Use a tiny allowed primitive set: path, ellipse, line, transform, opacity and optional simple clip. No arbitrary scripts, fonts, URLs, shaders or SVG markup in persisted settings.
2. `avatar-state`: pure reducer from normalized authoritative events and snapshots to semantic state. Handles sequencing, stale data, disconnect and multiple runs. No network calls or rendering.
3. `avatar-motion`: pure `samplePose(appearance, semanticState, transition, elapsedMs, seed, policy)` returning numeric draw parameters. No DOM, React, wall-clock randomness or platform APIs.
4. `avatar-web`: SVG adapter and one scheduler/visibility registry per document. A future Canvas adapter consumes the same pose.
5. Native adapters: same manifest and golden fixtures; equivalent sampler in Swift/C++/chosen platform language, or a shared compiled core if maintenance justifies it. Port the small contract before committing to a shared binary runtime.

Specify milliseconds, radians or degrees consistently, normalized coordinates, sRGB color, transform order, clipping, interpolation and clamping. Use integer-seeded PRNG with documented 32-bit semantics and golden random outputs across languages. Seed is generated once from stable bot UUID/installation binding and persisted; never depend on handle, list order, current time or `Math.random()` at render. Separate geometry seed from blink/gaze/effect streams so adding a motion channel does not change identity.

A seed plus local monotonic time makes replay deterministic for a supplied event timeline; it does not promise identical blinking on unsynchronized devices. Store transition start pose and interpolate to new target, avoiding jumps on interruption. Use absolute elapsed sampling or bounded analytic curves rather than accumulating physics errors each frame. Freeze decorative elapsed time while hidden; on resume paint current semantic state without replaying missed celebrations or catching up every frame.

Illustrative data contract (proposed, not an existing native API):

```json
{
  "schemaVersion": 1,
  "botId": "opaque-stable-bot-uuid",
  "revision": 12,
  "appearance": {
    "kind": "geometry",
    "manifestVersion": "1.0.0",
    "shapeId": "pebble",
    "color": "#8b5cf6",
    "seed": "a13f09c2",
    "motionVersion": 1,
    "customized": true
  }
}
```

Manifest contains provenance/license, immutable shape definitions, supported schema/motion versions, bounds and a known static fallback. Distinguish schema compatibility from visual asset version: editing an existing shape's path is a visible identity change and requires a new version or deliberate migration. Unknown shape/version renders a neutral static fallback while preserving opaque stored data; never silently overwrites it. Clamp every numeric input and cap serialized size (initial target: 2 KiB appearance record). Device motion preferences are separate from identity and do not travel as bot persona.

## Semantic state and event truth

“Thinking” is a friendly label for a verified active turn/preparation interval, not introspection into cognition or proof that a model is reasoning. Prefer “Preparing” when that is all the runtime knows. Animation cannot claim progress, successful tool execution or completed work on its own. Normalize actual Hermes build events behind a capability adapter; the names below are proposed internal semantics, not promises of existing wire event names.

| State                    | Required evidence                                                   | Visual treatment                                                                   |
| ------------------------ | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Unknown / reconnecting   | Missing/stale authoritative snapshot or lost stream                 | Still neutral face, distinct connection mark and “Status unavailable”; not “Idle.” |
| Idle                     | Fresh snapshot with no active run or unresolved attention condition | Rare seeded blink/gaze; no activity loop.                                          |
| Queued / preparing       | Accepted queued request or active turn, no verified running tool    | Deliberate look/squint; label based on verified stage.                             |
| Working                  | Matching live tool/job start until matching end/cancel/failure      | Bounded accent cadence. Tool name only if already authorized for display.          |
| Waiting / needs approval | Explicit wait/approval/input condition                              | Stable attentive pose and persistent accessible action label.                      |
| Failed / blocked         | Explicit failure or blocker still relevant to the selected scope    | Stable alert mark, no aggressive shaking/flashing.                                 |
| Completed                | Explicit successful terminal event for that run                     | One deduplicated brief effect, then idle if nothing else active.                   |
| Cancelled                | Confirmed stop/cancel result                                        | Settle without success effect; label “Stopped.”                                    |

Resolve evidence before visual priority: reject stale/out-of-order events by installation, bot, run, session and sequence; reconcile gaps from a snapshot. A terminal event only closes its matching run. Within current trusted state, priority is needs-attention/blocked → running tool → active turn → queued/waiting → fresh idle. A completed effect is an overlay permitted only when no higher-priority state would be obscured. Unknown connection freshness overrides claims about current execution, while already known unresolved approvals may remain labeled as last-known. Keep role/star, unread and connection badges orthogonal to face state.

For simultaneous runs, aggregate actual runs for the roster: preserve a needs-attention badge even while another run works. The selected chat uses its own session scope. Do not let a focused bot's busy state animate a different bot or installation. A lone tool-end event does not mean the whole turn succeeded. Deduplicate completion by event/run ID and do not celebrate historical completions on reconnect. Streaming text does not reset blink cadence. Lack of new tokens is not evidence of waiting, failure or completion; freshness thresholds must derive from the actual transport heartbeat/snapshot contract, not invented timeout guesses.

## Scheduler, accessibility and performance budgets

One scheduler per document/window, with explicit instance registration and disposal. Cache geometry and references. Use shared monotonic time, partition updates by visibility/detail tier, and write only changed attributes. Do not read layout in the frame loop, scan the document each frame, attach a timer/listener to every avatar or start a React state update per tick. Use [IntersectionObserver](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API) for visibility and [Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) for suspension; browser rAF throttling is helpful but insufficient as the sole policy. [requestAnimationFrame documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) also requires elapsed-time-based motion rather than assuming a refresh rate.

Start with these **targets to validate**, not measured claims:

| Dimension           | Initial acceptance target                                                                                                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Detail tiers        | Small roster: at most 15 painted fps when actually animating; active large preview: at most 30 fps. Idle faces sleep between brief movements.                                                                                  |
| Typical load        | 50 mounted / 20 visible avatars, mixed idle and active, at 32–40 px; include 1 large preview. Target avatar sampler + DOM writes p95 ≤2 ms per painted frame on named reference laptop, ≤4 ms on named midrange mobile device. |
| Stress load         | 200 mounted / 50 visible; 100 visible in a separate torture case. Degrade idle motion first, then active cadence, then static fallback. Record exact thresholds from measurements, not count-based folklore.                   |
| User responsiveness | No avatar-attributable long task ≥50 ms in a 60-second interaction trace. Scrolling, text selection, typing and opening Settings remain responsive under the same load.                                                        |
| Hidden/offscreen    | Zero ongoing avatar paint or polling callbacks after suspension settles; retain only observers/events needed to wake. Offscreen faces do not sample poses.                                                                     |
| Bundle              | Aim for ≤25 KiB gzip incremental core + web renderer + initial manifest, excluding existing framework; measure built output. No runtime asset requests.                                                                        |
| Memory              | Aim for ≤5 MiB incremental retained JS heap for the typical fixture after warm-up; separately report DOM, raster/GPU memory where tools expose it. No growth after 20 mount/unmount cycles.                                    |
| Power               | Compare static and animated fixtures over a repeatable sustained run on real battery hardware; report hardware, OS, refresh rate, duration and process/energy metric. Do not promise a battery percentage from JS timing.      |

If p95 cost exceeds budget over repeated sampling windows, lower decorative cadence and pause inactive rows before switching renderer. Use hysteresis to avoid quality oscillation. Never drop semantic state updates or text labels when degrading visuals. Limit raster backing scale if Canvas is later used; report DPR and resolution. An rAF loop that wakes at 60/120 Hz to paint at 15 Hz still has scheduling overhead: use one shared deadline/wake policy, park fully between sparse idle events, and measure callback counts as well as painted frames.

Respect [prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion) at startup and live changes. Reduced motion renders static state poses and text/badges, with no blink, gaze drift, bounce, pulse or particles. Provide Settings → Appearance → Motion: System / Reduced / Off; Off is fully static. A battery-saver option may reduce animation further; browser battery APIs are not a portable dependency. Native hosts can supply reliable low-power/thermal signals; web uses explicit preference and measured load, without fingerprinting hardware.

Keep adjacent names/status text accessible. Decorative SVG is `aria-hidden`; controls have labels, keyboard navigation, visible focus and selected state. A status change may update a restrained live region, not narrate every blink. Preserve legibility at 200% zoom, high contrast/forced colors and small sizes. Completion must not rely on motion or color. No rapid flashes or perpetual attention effects. Hidden/minimized/background native windows follow equivalent lifecycle rules.

## User-supplied photo avatars

Photo is a first-class alternative to the animated shape, available during primary-agent confirmation and later Settings. Use **Animated shape / Photo**, with a local file picker, preview, crop confirmation, Replace, Remove photo and return-to-shape actions. Keep the previous geometric shape/color/seed so switching back does not invent another identity. A photo remains still; adjacent activity text, attention/connection badges and the independently derived orchestrator star remain available. Photo instances do not join the animation scheduler.

Use a discriminated appearance contract: `kind:geometry` has a bundled manifest/shape/color/seed; `kind:photo` has an opaque owner-Hermes asset reference, revision, dimensions and media type. Never store raw photo bytes in the app authentication database, model context, transcript, vendor infrastructure or public release artifacts. Do not accept arbitrary image URLs. Rendering a photo does not grant access to other native assets or paths.

Start the web picker with JPEG, PNG and WebP, bounded file size, decoded dimensions and pixel count. Detect content signatures rather than trusting extensions/MIME labels, honor orientation, preview the crop, then normalize to a small static raster. Strip EXIF/GPS and original filenames; keep only the normalized avatar. Client checks improve feedback but the authenticated owner-Hermes upload handler must independently validate/decode/re-encode under resource limits. Normalization failure rejects the upload; do not reuse native helper behavior that falls back to the unnormalized original. HEIC support needs an explicitly tested native/browser conversion path and a clear unsupported-format response until then. No avatar generation, face recognition or image-model call is required.

Reuse verified `profiles.get_asset` / `profiles.set_asset` through an avatar-specific adapter bound to the exact existing profile and permitted avatar key. The native image lives outside the metadata namespace; coordinate asset receipt and full-namespace read/merge/CAS with resumable results. Do not claim those stores update atomically. Read asset bytes directly from authenticated Hermes into browser-local image memory; never put a credential in an image URL. Keep private images out of public caches/CDNs. Switching appearance modes can retain the existing photo reference; explicit removal clears the owned reference and deletes only assets no longer referenced, with a defined retry/cleanup policy.

The playground includes **local-only** photo selection, a centered crop, raster normalization and switching back to animation. Files never leave that page/device, selections disappear on reload, and the demo does not implement server upload, persisted removal or a crop editor. Automated tests use a synthetic image, reject disguised SVG content and verify zero upload requests. Production photo persistence and security remain integration gates.

## Onboarding, Settings and owner-local persistence

Extend the existing planned **confirm primary agent handle** step with “Choose a look” and color swatches. Keep the verified detected agent and its identity binding; do not introduce an orchestrator roster picker. Show a reasonable default or existing native appearance, and let the owner keep it with no added mandatory step. The next action still opens that same native agent's workspace. Registration, appearance preview and persistence make zero model calls; the separately authorized welcome remains governed by the onboarding plan.

An avatar change changes appearance only: no native profile rename/move/clone, SOUL/persona/memory/model/tool/channel alteration or history rewrite. Orchestrator is a separately derived role badge. A handle change does not reseed or recolor the face. Settings → primary agent → Appearance offers the same picker, preview, reset-to-default and save/cancel behavior. Later enabled bots use the same component with their stable IDs. Preview is local and reversible; Save is one authenticated revision-checked operation.

Use the owner-Hermes plugin's durable metadata store as authority, keyed by installation + stable bot UUID. Browser storage is only a cache/draft, never the sole source. A future native client and the web app consume the same normalized appearance contract. Proposed plugin mutation takes expected revision and idempotency key; validates caller/bot binding, schema, size, allowlisted shape and solid color; returns committed appearance and revision. Optimistic UI rolls back or offers retry on conflict. Crash/retry cannot create a different seed or duplicate profile.

Interoperate with current `ui_meta['hermes-bots']` using read/merge/CAS of the **entire namespace**, preserving title, description, sections, groups, pinned, hidden, image fields and unknown fields. Store extended appearance in a plugin-owned versioned record; project compatible `shape`, `color`, `custom:true` into native metadata through an adapter. Until native knows an original shape ID, project a deliberately chosen supported fallback and retain the canonical original record. Do not write unsupported IDs into a legacy renderer and assume it works. Record the projection revision/hash so native edits can be distinguished from stale echoes.

Import existing explicit choices before defaults. Preserve uploaded/generated/pet image kind and asset reference; show “Current image” until the owner explicitly chooses geometry. Image assets follow the verified native asset API, not an inline metadata patch. Native edits to known shape/color after projection need a deterministic reconciliation rule: import a newer verified explicit native edit or surface a conflict, never silently revert it on reconnect. Unknown fields round-trip intact. Older builds without reliable namespace CAS must block unsafe writes or use a proven serialized plugin adapter; do not emulate safety with a browser lock.

Appearance/schema support is negotiated per installed native build. First rollout must test the pinned af0 and older 29112 compatibility targets from the existing plans; af0 findings alone do not prove 29112 support. Failed appearance save should offer retry or keeping the verified existing appearance, without invalidating completed owner authentication or creating another welcome. Onboarding replay must retain its detected primary binding.

## Security and operational boundaries

Persist data, never executable animation definitions from an owner/model payload. Reject external image URLs, arbitrary SVG strings, scripts, CSS, path traversal, oversized geometry and unbounded loops in this geometric feature. Trusted bundled manifest revisions are reviewed and integrity-checked with the app release. Escape labels; renderer parses only a small schema. No remote fonts, CDN runtime, dynamic vendor asset downloads, avatar analytics or motion telemetry. Local opt-in benchmark diagnostics contain counts/timing, not handles, prompts or conversation content.

The appearance endpoint uses the same owner authentication, origin checks, authorization and identity directory as other planned mutations. A bot's suggestion is not owner approval to change another bot's identity. Appearance state cannot grant tools or change native routing. Offline rendering works from the shipped bundle and cached appearance; offline editing is a draft until the authoritative save succeeds. Rendering never writes Hermes files. No owner's live profiles, model provider settings or Hermes services should be changed for the research/demo phase. The isolated demo may be served by the existing preview web host.

## Delivery phases and acceptance

1. **Isolated prototype:** original bundled geometry, state selector, color/shape picker, many-avatar fixture and shared scheduler. Clearly label states as simulated. Include reduced/off motion and hidden/offscreen controls. No production chat-flow changes, backend calls, model calls or metadata writes; the demo uses its own isolated HTML entry. Review at 24, 32, 40 and 96 px in light/dark themes.
2. **Measure and freeze contract:** record baseline and candidate traces; benchmark SVG before choosing another renderer. Freeze manifest v1, PRNG/pose fixtures, state priorities and fallback policy. Resolve license provenance. Publish measured results separately from the targets above.
3. **Backend and identity adapter:** implement the proposed validated persistence, import/projection/reconciliation and CAS/idempotency contracts behind capability checks. Test identity/rename invariance, concurrent native/web edits, unknown versions, image preservation and restart recovery using fixtures, not live owner profiles.
4. **Onboarding and Settings:** integrate the same appearance component into the planned verified-primary step and later Settings, after authentication/detection prerequisites exist. Verify save failures, retry, cancel, reset, reload and cross-device fetch. Assert no extra welcome/model calls and no native identity changes.
5. **Live state integration:** bind to verified per-build activity events and snapshots. Cover tool start/end, streaming, queued work, approval, cancellation, reconnect gaps, duplicate terminal events, simultaneous runs and cross-installation profile-name collisions. Unknown stays unknown.
6. **Native feasibility spike:** choose app framework independently, then implement one Apple and one Windows adapter or validate a chosen shared webview. Compare the same geometry/pose fixtures and lifecycle policy before promising consistency. Expand only after the spike proves maintenance, power and accessibility costs.

Acceptance evidence must include:

- Pure reducer tests with sequence gaps, old events, two runs and two identically named profiles on different installations; verified priority and effect deduplication.
- Deterministic pose/PRNG fixtures at defined timestamps and interruption points, independent of refresh rate. Cross-renderer geometry/pose tolerance plus human review; exact pixel equality is not realistic across antialiasing engines.
- Browser traces on current supported Chrome/Edge, Firefox and Safari desktop, plus real iPhone/iPad Safari if supported. Name hardware, OS/browser version, zoom, DPR, count visible/mounted, state mix and power mode. Test refresh rates above 60 Hz and slow CPU conditions.
- Instrumentation reporting frame callback count, actual painted fps, p50/p95/p99 sample/write time, long tasks, DOM node count, retained heap, and whole-frame paint/composite costs. JS sampler timing alone is not end-to-end rendering performance.
- Hidden tab, offscreen list, minimized window, navigation and repeated mount/unmount tests showing correct pause, cleanup and state recovery. Verify no reconnect celebration storm and no background polling for animation.
- Keyboard/screen-reader review, live reduced-motion changes, high contrast and both themes. Selected avatar/color remains clear without animation.
- Persistence/security tests for wrong owner/bot, conflicts, oversized/malformed records, unsupported schema, concurrent native edit, network loss after commit and retries; native identity/history/persona preserved.
- Native spike results on actual Apple and Windows hardware, including low-power/background/thermal handling. A browser demo proves only that browser/demo combination.

## Open decisions

The first web renderer is recommended; final roster capacity and cadence remain measurement-dependent. Native app frameworks and shared-webview versus native rendering are unresolved. The precise deployed Hermes event contract, stale-stream threshold and older-build avatar metadata behavior need compatibility tests. The final art family/palette and desired motion intensity need review in the local playground. Native-source reuse requires pinned license review. None of these uncertainties prevents an isolated original SVG demo or a renderer-independent specification.

Technical native options: [Apple SwiftUI Canvas](https://developer.apple.com/documentation/swiftui/canvas) is a candidate immediate-mode drawing surface, and [Microsoft Win2D](https://learn.microsoft.com/en-us/windows/apps/develop/win2d/) provides a candidate Windows 2D path. These establish available drawing approaches, not completed ports or parity guarantees. Keep shared semantics and fixtures authoritative whichever platform surface is eventually selected.
