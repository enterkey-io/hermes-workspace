# Execution plan: owner onboarding, identity and connections

15 October 2026. **Unimplemented plan, not a completion report.** Companion to [product behavior and evidence](ONBOARDING_AND_CONNECTIONS_PLAN.md). Work is ordered to preserve the working native Bot Mode preview while replacing preview pairing with a private installed product. No owner deployment, real provider calls or releases are authorized by this planning document.

## Delivery order and blocking spikes

Deliver one authenticated vertical slice first: Node/SQLite and owner Cloudflare adapter → durable plugin issuer trust → browser reconnection → native identity discovery. Do not expose agent/connection mutation services behind a decorative login or postpone real trust until after management UI.

| Stage                              | Concrete work                                                                                                                          | Exit evidence / dependency                                                                              |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 0. Contract and fixture inventory  | Freeze schema v1, method allowlists and two pinned native adapters; record capabilities rather than infer from marketing versions      | Both pinned sources exercised with disposable homes; zero owner mutations/model calls                   |
| 1. Owner auth + trust              | Bootstrap, login/session/recovery, app adapters, installation enrollment, tickets, expiry/revocation, route diagnostics                | Competing bootstrap and independent-host restart/reconnect suite passes on both deployment adapters     |
| 2. Identity and primary enrollment | Root/default detection receipt, stable bot directory, canonical binding, public handle validation and native route adapter             | Default vs named launch matrix; preserved native files/history; custom-handle DM/room/resume gate       |
| 3. Management backend/runtime      | Policy, approvals, receipts, real `workspace_agents` tool, bundled skill, current-turn role context, actual creation/enable/attach     | Correct runtime caller and profile/DM loading; no self-elevation; partial creation repair               |
| 4. Connections backend             | Redacted catalog/import, approved recipes, native auth/token reuse, restricted web OAuth callback, tests, attachments and invalidation | One certified path per auth class; denied/expired/revoked/uncertain tests; no credential leaks          |
| 5. First-use and compact UI        | Owner login → detected primary → handle → real welcome; Connections cards, bot settings, team/role/reporting review                    | Product flow works at phone/laptop sizes; no manual pairing or developer relay                          |
| 6. Install/migrate/recover         | One-agent installer, supervision, preview migration, versioned backups/update/rollback, full gate record                               | Clean install and migration end-to-end on each deployment/native matrix; release gate only then changes |

Stages 2–4 may develop behind disabled capabilities after stage 1; stage 5 must not promise unfinished features. The first usable slice can reconnect to existing native chats before agent creation ships, but full requested launch still requires management and connection gates.

Resolve these spikes with narrowly scoped fixtures before choosing implementation details:

1. **Auth library/adapters:** maintained authentication implementation compatible with Node SQLite and Worker/D1, atomic one-admin bootstrap, durable rate limits and equivalent cookies/CSRF. Better Auth remains a candidate, not a verified decision. Pick one only after tests; no hand-written password cryptography.
2. **Caller and prompt runtime:** prove reliable profile/session identity in plugin tool calls, native DM subprocess and resumed Bot Chat. Prove per-turn context can reconcile native “You are @hermes” with a changed public handle without rewriting SOUL. If supported hooks cannot safely mediate mandatory native `message_agent` routing, add an explicit verified adapter or gate custom handles; never silently patch core or rename the profile. A failed gate blocks the requested custom-handle launch experience.
3. **Web OAuth using native engine:** gateway `client_redirect_uri` accepts only HTTP loopback in both builds; a browser cannot act as Desktop's listener. However both builds' `hermes_cli/web_routers/mcp.py` implement a dashboard `DashboardOAuthFlow` with externally reachable redirect and native token storage. Reuse that underlying native flow/worker through a narrowly authenticated plugin adapter, not by exposing the dashboard or bypassing its auth. In af0 inspect `_mcp_oauth_callback_url` (67), auth start (251 onward), callback (339 onward), `tools/mcp_dashboard_oauth.py`, `hermes_cli/web_server_mcp.py`; older corresponding auth start is 237, with callback/worker helpers in `hermes_cli/web_server.py` around 13741/13764 rather than af0's separated worker module. Certify each provider's redirect rules. A pinned client/loopback registration can still require same-machine/forwarded setup and cannot be relabeled one-click browser OAuth.
4. **Actual activation:** prove tools, selected skills and MCP permissions in an existing long-lived session and DM recipient. Respect deferred Python tools/prompt sections; an explicit safe session rebuild must preserve canonical lineage/history and not interrupt active work. No “ready” from configuration alone.
5. **Task coordination:** determine whether pinned native task primitives meet dependencies/results/idempotency; otherwise specify durable plugin coordinator and prove orchestrator → leader → specialist reporting separately from chart editing.

## Components and authority boundaries

Proposed paths are implementation targets, not files created by this pass.

| Component                           | Responsibility / persistence                                                                                                            |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core` shared schemas      | Versioned identity, capability/readiness, request/approval/error/result contracts; runtime validation; no secrets                       |
| New `packages/owner-service`        | Fetch-style bootstrap/auth/session/config/ticket routes and policy-independent transport contract                                       |
| New Node owner adapter              | SQLite transactions, durable limiter/session/setup state, local secret directory, maintained auth library integration                   |
| New Cloudflare owner adapter        | Same contract, owner account D1 + Worker secrets/assets; equivalent transaction/uniqueness semantics                                    |
| `plugins/bot-web` native adapters   | Native revision-specific safe operations, root/profile proof, canonical Bot Mode, credential storage and session activation             |
| New plugin workspace store/services | Owner-Hermes transactional identity/team/role/grant/proposal/operation state, issuer trust, resource references, private audit metadata |
| `packages/hermes-client`            | Authenticated direct transport, ticket renewal, reconnect/reconcile, capability discrimination; no opaque arbitrary-RPC escape hatch    |
| `apps/web`                          | Forms, cards, recipient/approval review, states, search/navigation; no authorization decisions or duplicate native mutation logic       |
| Installer/operator commands         | Idempotent install/enroll/doctor/repair/recover/update/rollback; no default public secrets                                              |

App database stores admin hashes/library auth data, sessions, setup claim consumption, rate limits, endpoint configuration, installation binding and signing-key metadata. Private signing key stays in owner secret storage. Plugin database stores workspace metadata, grants, operation receipts and trusted issuer keys. Native Hermes owns profile content, model credentials, service tokens and transcripts. The browser holds tickets/drafts in memory; no token in URL/localStorage. The app server never stores message drafts, SOUL, history or service credentials. Public connection metadata must not be bundled into vendor assets/analytics. Installer diagnostics redact endpoints unless the owner explicitly exports them locally.

## Versioned data contracts

Use UUIDs for app/workspace/bot/team/connection/request IDs, integer revisions and ISO UTC timestamps. Reject unknown privileged fields. ID references are always scoped to installation/workspace, not global profile-name strings.

- `InstallationBinding {id, pluginBindingId, nativeInstallId?, nativeRevision, trustEpoch, capabilityRevision, endpointId}`. The old build's plugin ID is persisted at root; a future native ID enriches rather than replaces binding.
- `DetectionReceipt {id, installationId, outcome, primaryProfileRef?, launchProfileRef?, evidence:"native-default-root"|"verified-operator-binding"|"persisted-workspace-binding", rosterRevision, complete, checkedAt, expiresAt}`. Store server evidence; browser cannot supply profile path or turn failure into success.
- `Bot {id, installationId, nativeProfileRef, nativeSelector, identityGeneration, canonicalRootRef?, handle, handleRevision, displayName, roleCardId, teamId?, managerBotId?, enrolled, readiness}`. Native selectors are adapter-owned; expose only necessary public forms.
- `HandleAlias {normalized, botId, status:current|retired, introducedRevision, retiredRevision?, releasableAfter?}`. Unique normalized namespace includes reserved native collisions. In-flight messages bind bot IDs, never mutable aliases.
- `RoleCard {id, revision, title, description, responsibilities, boundaries, expectedOutputs}`. Native top-level profile description gets a bounded routing summary; SOUL remains separate. Mirrored UI namespace uses native expected revision.
- `Team {id, name, order, revision}` and `Workspace {id, revision, orchestratorBotId, initializedAt}`. One root constraint; every enrolled reporting chain reaches it; no cycle/self-manager. Team membership is independent of manager/dependencies.
- `ServiceRecipe {id, nativeCatalogId?, nativeBuildRange, source, recipeRevision, transportKind, authKind, requiredFields, scopes, installEffects, supportsWebCallback, supportState}`. Avoid runtime arbitrary URLs/commands supplied by model.
- `Connection {id, installationId, nativeResourceRef, ownerProfileRef, recipeId?, accountLabel?, configRevision, authState, discoveryState, lastTest?, externalManagement?}`. Secret references stay opaque. No raw key/token/value in response types.
- `Attachment {id, botId, resourceId, allowedToolIds, skillIds, revision, savedState, runtimeState, runtimeSessionRef?, effectiveRevision?}`. Add/remove deltas, not whole-list overwrite defaults.
- `Proposal {id, actorPrincipal, action, normalizedSpecHash, targets, expectedRevisions, requiredGrants, expiresAt, idempotencyKey, status}` and `Approval {proposalId, approvedSpecHash, ownerSessionId, approvedAt}`. Approval cannot authorize later changed arguments.
- `Operation {id, proposalId?, kind, targetIds, specHash, phase, status, nativeReceipts, verifiedPostconditions, retryClass, errorCode?, createdAt, updatedAt}`. Durable phases support reconciliation; uniqueness on actor/kind/idempotency key and same-key/different-spec conflict.
- `Welcome {workspaceId, botId, version, intentId, status:not_started|submitting|uncertain|accepted|completed|failed, nativeMessageRef?, nativeTurnRef?}`. Exactly-once intent/at-most-once safe resubmit, not a promise of exactly-once remote execution without native evidence.
- `Task {id, assigneeBotId, dependsOn, expectedResult, reportToBotId, state, resultRef?, revision}`. Final verified result advances dependencies, not message queue acknowledgment.

Readiness is factored: configuration `absent|saved|invalid`; auth `not_required|missing|pending|authorized|expired|denied`; discovery `untested|testing|passed|failed`; attachment `absent|pending|saved`; runtime `unknown|ready|refresh_required|unavailable`. A server being `configured`, `lazy`, or token-present cannot imply runtime ready. Report exact check timestamp and profile/session revision.

## API operations and authorization

Owner app routes (all responses `Cache-Control: no-store`): `GET /instance/status` reveals only setup/sign-in state; `POST /bootstrap` consumes proof + creates owner atomically; library login/logout/session endpoints; `POST /sessions/revoke`; `GET/PATCH /instance/config` (owner, expected revision); `POST /hermes/ticket` (owner + CSRF). Recovery is an owner-local operator command, never a public reset without proof. Bootstrap credential never appears in a URL, referrer or app bundle; persist only verifier/hash and expiry.

Plugin exposes a versioned restricted RPC surface: `installation.describe`, `workspace.detect_primary`, `workspace.initialize`, `workspace.describe`, `bots.list`, `bots.update_handle`, `roles.update`, `teams.*`, `workspace.set_orchestrator`, `agent.enable/create/update/attach`, `requests.list/approve/deny/status`, `operations.get/resume`, `services.catalog`, `connections.list/prepare/configure/auth_start/auth_status/auth_cancel/test/attach/detach/disconnect`, and `workspace.message`. Names are proposed; freeze them in stage 0. Native existing chat/room/routine methods remain individually allowlisted. Never allow ticket holders to call arbitrary native RPC, shell, pairing administration or issuer enrollment.

All mutation responses return operation ID, state, effective revision, verified effects and retry action; failures use `unsupported`, `not_authenticated`, `forbidden`, `stale_revision`, `ambiguous_identity`, `requires_approval`, `requires_auth`, `partial`, `uncertain`, `temporarily_unavailable`. `202 pending` is not success. Reject actor/caller fields in model arguments. Tool runtime passes a sealed server-generated principal bound to profile/session; web obtains an owner principal from validated ticket scope. Model tool has no owner approval or issuer-management actions.

No grant derives from role prose. Default bot policy is request-only for mutations; owner may issue bounded standing grants to any bot for approved action/resource classes, creation counts and expiry. Grants never include self-granting, owner approval or root transfer. Recheck grants, catalog revision, target revision and graph constraints at execution. Audit only actor/action/resource IDs, outcome and timestamps, excluding prompts/secrets.

## OAuth and secrets contract

Preferred callback is an operator-configured HTTPS path on the owner's Hermes bridge route, reusing native `DashboardOAuthFlow` and PKCE/token store. This keeps the app service outside the OAuth credential path and works with an app server unable to reach Hermes. Callback URL is fixed from enrolled configuration, not request Host headers or model/user arbitrary redirect input. Browser must be able to reach the bridge after provider redirect; provider registration must accept that URI. A private-only owner VPN path can work for browser-delivered redirects only if that provider accepts it; do not imply all providers do.

Flow record binds connection/profile/owner principal/recipe/config revision/state/issuer/redirect/scopes/expiry and one active attempt. Start/poll/cancel require owner access; callback receives provider state/code, validates exact state and issuer, single-use/expiry, then native worker exchanges using PKCE. No bearer ticket in callback URL. Callback serves a minimal no-store page with no third-party assets, strips sensitive URL state, and redirects only to a fixed owner app destination with an opaque result reference. Never relay token or code into a model message. Redact proxy/query/request logs. Enforce endpoint/redirect/resource discovery policy against SSRF, credential-forwarding and unreviewed private destinations; owner-approved local endpoints are deliberate exceptions, not automatic URL fetches.

Both pinned builds have native dashboard OAuth primitives, but their reuse under plugin authentication, flow ownership, exact redirect registration, cancellation, refresh and restart behavior is unverified. Gateway loopback support alone is insufficient. Providers with fixed loopback client registrations expose “Requires local setup” with explicit instructions and reusable imported authorization; they are not launch-certified web sign-in recipes. Failed/restarted in-memory OAuth flows expire and can restart after checking stored auth; never silently claim resumed consent.

For API keys, owner-only masked form posts directly to Hermes with size/type validation. Keep credentials in native restricted storage/references; validate with a non-destructive test. Do not blindly forward `mcp.servers.set_api_key`: af0 replaces HTTP headers with an Authorization/Bearer reference, so custom headers and x-api-key/basic-auth recipes require verified scheme-specific adapters, read/merge/revision protection and readback. Likewise `mcp.servers.add` preset configuration is not proof that catalog code bootstrap installed anything; keep code-install-required distinct. Preserve old working credential until replacement passes where native primitives permit; otherwise stage/restore using adapter-managed transaction/backup with restrictive permissions. Test failure never echoes a key. OAuth/config operations must not auto-select every discovered tool just because native catalog defaults do; hold attachment until reviewed finite allowlist is written and read back. Newly discovered tools stay disabled pending approval.

## Native mutation discipline and runtime behavior

Use native operations, inspect all `applied`/readiness fields and read back effective state. Creation explicitly disables credential mirroring, cloning/channels and shell aliases; approved provider access is granted narrowly. On af0 `ok:true, model_set:false`, retain a partial operation and offer provider repair—no second profile, no broad env copying. Preserve profile creation receipt for resumable next steps.

Metadata writes read the entire `ui_meta['hermes-bots']`, merge only owned fields and CAS; retain avatar/title/unknown metadata. Resolve races with reread/review rather than destructive last-write-wins. Empty `enabled_toolsets` means native defaults, not zero tools. Installed skills default enabled: derive disabled complement from installed snapshot, detect new installations and verify effective permissions. Attachment removal must not translate to a native reset that widens access.

Before each turn, supply current role, root/manager, identity directory revision and effective grants through a supported bounded hook; expose authoritative describe tool for details. A frozen system section is insufficient. Role/handle edits invalidate pending proposals tied to old revisions; in-flight work keeps its bound recipients and authority snapshot but must recheck permission before later external actions. Do not rewrite past transcript text. Runtime updates wait for safe boundaries or clearly require a safe rebuild; Stop is separate and explicit.

## Migration, restart and repair

Inventory preview version/routes, native compatibility and current enrolled profiles without mutation. Back up owner plugin/config state and record native IDs/canonical roots; do not copy credentials to the app host. Install owner runtime and persistent keys, claim owner via private credential, enroll trust operator-side, verify a signed ticket connection. Read current native Bot Chat and pending work before enabling sends. Then mark preview pairing migrated; revoke legacy browser grants after verified cutover, with an explicit rollback window. No automatic pairing reauthorization on refresh, restart or new device.

Reconnection uses bounded jittered backoff; actions remain disabled while identity/history/approvals are unreconciled. Fetch canonical current lineage, in-flight work and pending approvals before allowing a send. Never replay uncertain messages, approvals, create or attach calls. Reopen should preserve selected bot by stable ID, not stale session pointer. Endpoint relocation requires owner-verified same installation/trust; mismatched identity is blocked.

Installer maintains a versioned manifest of components, migrations, file ownership, state locations and completed stages. Reruns verify/reuse valid state; missing keys trigger repair rather than silent key replacement. Supervision uses host-native service management or containers. Updates snapshot compatible stores, migrate transactionally, smoke-test native connection and rollback executable/config only where schema compatibility is proven. New native conversations/agents created after update must not be erased by restoring an old blanket home backup. Downgrade refuses incompatible store schemas with a clear repair route. OAuth pending attempts can restart; established authorized resources and receipts persist. Owner-local recovery rotates/revokes affected sessions/trust and never deletes Hermes identities.

Publish versioned web-app and plugin artifacts on GitHub, with independent requirements and install commands. The installer preflights the selected app adapter's supported runtime, persistent owner-state storage, HTTPS origin, secrets and service lifecycle, separately from Hermes's runtime/profile/plugin requirements. Measure and publish minimum host resources from the certified packaging rather than guessing. A host that serves only static files cannot provide the required administrator service by itself. Plain-language instructions explain which component goes on which chosen host, with no same-server requirement; hosting suggestions remain optional and do not imply a vendor account is necessary.

## Exact acceptance suite and launch gates

Run disposable configuration/security fixtures first on both pinned revisions. Runtime model/provider tests require separately authorized test accounts/fixtures; source inspection or mocked tools never count as runtime passes. Record revision, adapter, platform, evidence class and observed result for each gate.

1. **Ownership:** simultaneous valid bootstrap attempts create exactly one admin; invalid/missing/expired/replayed proof cannot claim; public URL alone cannot claim; restart preserves owner/session/rate limits; recovery requires host ownership. No plaintext passwords or setup secrets in storage/logs.
2. **Independent hosting:** Node app and Cloudflare app each succeed while their runtime cannot connect to private Hermes; browser can. First login, refresh, reopened tab, new-device login, app restart and bridge restart recover without pairing/agent intervention. CORS exact origins, forged/expired/wrong issuer/audience/algorithm tickets fail. Open stream ends at TTL; session revocation obeys documented bound; running job is not falsely reported stopped.
3. **Primary matrix:** root launch, named-profile launch, sticky active named profile, custom Docker root, sorted/reversed roster, zero/multiple defaults, partial roster, permission failure and mismatched/cloned installation. Without a prior explicit verified primary binding only verified root/default is selected; test an operator-bound named-primary installation separately, and reject launch/sticky-profile guesses. All ambiguity cases make zero model/profile mutations.
4. **Preservation:** hashes/snapshots of existing SOUL, memory, channels and model configuration remain unchanged except explicitly authorized narrow plugin activation. Existing histories/canonical root retained; no placeholder/clone/move/rename. Initialization retry after every phase yields one enrolled primary/root.
5. **Handles:** keep `@hermes`; set custom handle; edit in Settings; race same handle; case variants; native ID/friendly alias/reserved collisions; old alias in in-flight work; deleted/recreated native profile. Correct stable recipient across direct chat, native DM sender/receiver, room mention and resumed chat on both builds. Native prompt `@hermes` does not cause contradictory public identity or misrouting. Unsupported mediation blocks custom-handle certification rather than hiding discrepancy.
6. **Welcome:** zero calls during discovery/registration; one explicitly authorized welcome; interrupted response/reload reconciles before any retry; provider denial yields honest failure; no fake assistant message, invented team or unauthorized setup actions.
7. **Management:** model can actually see/call tool and read skill from default, named and DM subprocess; caller spoof/missing identity rejected; second authorized bot can propose new profile; cannot approve itself/change root/elevate. Approve exact spec, expire/deny/replay/change-revision cases. Kill after native create; retry gives same partial profile. af0 model failure repaired without broad credential copying.
8. **Organization/runtime:** one root, no cycles/orphans, team leader tree, preserved unknown UI metadata under stale CAS, role/name/handle/SOUL independently editable; existing long-lived chat receives new role next turn. Task dependency does not advance on DM queue acknowledgement; duplicate reports/restart do not double-run dependent task.
9. **Connections/auth:** reuse preexisting connection without credential export; same name different account/profile not merged; tested OAuth browser return on independent hosts, wrong-state/issuer/expired/replayed/cross-profile callback, denied consent/cancel/popup blocked/network loss/restart. API-key and no-auth/local cases show appropriate forms. New local code/scopes require owner review. Fixed-loopback provider correctly marked unsupported for web auth.
10. **Effective permissions:** explicit bot/tool allowlist before attachment; broad native defaults never leak new tools. Saved/token-present/discovered/runtime-ready are distinct. Existing chat and native DM get the approved tools/skills, unapproved bot cannot use them through management route, revocation prevents future calls and reports inability to revoke provider token separately. Shared-OS non-isolation limitation remains accurate.
11. **Repair/update/privacy:** kill at each receipt/config phase, rerun installer, rotate issuer, remove required key, relocate endpoint, update/rollback; no duplicate agents or lost identity/history. Browser/app/plugin/proxy logs contain no service credentials, tickets, OAuth codes or transcripts. No vendor request receives endpoints/content/session data. Public assets/cache never disclose owner configuration.
12. **Usability:** one installer returns usable URL, owner setup requires no ports/CORS/API-key relay, detection does not ask to choose root, handle editable later, Connections can be skipped, large roster search/scroll works, focus/draft isolation/history usable on phone/laptop. No nonfunctional controls or unsupported service promises.

Full launch requires all core gates on both advertised native builds and both owner deployment adapters. A narrower supported release may omit an optional recipe only with explicit capability gating and honest UI, never by claiming untested parity. Publish machine-readable evidence with failing/pending gates retained; amend current release checks only after actual end-to-end results. This research creates no release eligibility by itself.
